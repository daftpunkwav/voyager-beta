Parity 原则深度评估 ⭐

用户与 agent 平等 · 唯一例外是 secret

§2.1 铁律 7:"Parity(对等),隐私除外:用户能在应用里做的,agent 经同一 capability 也能做——唯一例外是隐私项。Parity 成立的必要条件:状态落在共享基座 + 能力收进注册表;客户端外壳(chrome)的私有状态不参与 parity。"

2.1 Parity 总览

✅ 完整 Parity · 24 项(48%)

主题/字号/设置/笔记 CRUD/图谱/资源/LLM/路由跳转/subagent 注册/活动页 undo。
核心业务层全部到位,且有测试覆盖(test_settings.py、test_capabilities.py)。

▲ Parity 失败 · 12 项(24%)

关闭 AskUser 弹窗、关闭 ImportDialog、关闭 SpawnForm、清空 chat 草稿、滚动定位、切换 graph 顶栏、急停运行中 agent、FloatingChat 展开/收起、collapse 侧边栏、Electron 窗口控制……

🔒 隐私例外 · 2 项(4%)

LLM api key + GitHub token:服务侧显式拒绝 agent(llm/capabilities.py:138-147 + repo/capabilities.py:152-157)。
双重门(平台层 + 服务层)强制,符合铁律 7 隐私例外。

2.3 5 个最严重的 Parity 违反

🔴 #1 用户能关闭 AskUser 弹窗 / 清空草稿 / 折叠面板,agent 完全不能

这些操作全部走前端 useState / zustand 局部状态:

  • FloatingChat.tsx:21-25 · useFloatingStore · 展开/收起
  • ChatPage.tsx:12 · useState draft · 草稿
  • chatStore.ts:200 · clearQuestion · AskUser 弹窗
  • SettingsPage.tsx:18 · useState active · 设置子页
  • GraphPage.tsx:28 · useState · 顶栏面板

违反"系统任何操作,人和 agent 都可执行"。当用户关闭了 agent 刚弹的 AskUser 弹窗,agent 端只能 asyncio.wait_for 120s 超时,期间阻塞任务流,违反铁律 §2.1 第 7 条(Parity,隐私除外)。

🔴 #2 没有 kill switch / 急停运行中 agent 的 capability

用户在前端无急停按钮:grep -E "kill|abort|emergency|stopAgent" 全部 0 命中。 graph.cancel_index 只允许取消排队的任务(graph/capabilities.py:61-64);运行中任务的协作式停止声明"在演进中"。 agent 同样不能终止已派出的 running subagent —— 双方都缺。长任务无安全阀,违反用户对"急停"的基本预期。

🔴 #3 apps/desktop/ 目录完全空白 —— Electron 端 Parity 无法验证

架构文档中 apps/desktop/{shell, file-bridge, browser-host} 三个目录不存在(glob 返回空)。 Electron 端的窗口控制、关闭、最小化、托盘、自动更新、文件对话框/拖拽桥都未实现。 这意味着桌面 chrome 层的 Parity 在生产前完全无法验证。

🔴 #4 用户没有"为 agent 设置全局能力白名单"的 UI 入口

AppPolicy(allowed=frozenset(...)) 机制在 agent/policy/engine.py:28-33 就位,测试 test_policy.py:55-58 覆盖; 但 PermissionMatrix.tsx:7 是只读跳转 /settings?module=agent,真正改白名单的 UI 路径缺失,只剩 subagent 级 allowed_tools 勾选(SpawnForm.tsx:19-26)。 用户"为 agent 设置权限"实际只能到 subagent 工具面级,AppPolicy 级缺失。

🟡 #5 跨进程边界 restrict() 未一致强制

ActorContext.restrict() 是收窄(platform_actor/context.py:23-30),test_actor.py:50-59 覆盖纯函数级; 但 platform_capability/guards.py:122-182 的 execute() 全文未出现 restrict 引用,handler 拿到 _actor 后自由使用,scopes 仅在 capability 声明上做匹配。 若下游服务信任上游传入的 actor,需要在每条边界显式 restrict,这点当前由 capability.scopes 声明间接保证,但无测试覆盖。

2.4 隐藏 Bug:applyCodeFont 未实现

设置项可改但效果不可见 —— set_code_font 是 settings 可改,useTheme.ts:58-60 收到 settings.changed 事件时只 applyTheme 和 applyFontScale,没有 applyCodeFont。 违反"用户能改的,效果可见"的隐含 Parity 原则。需在 useTheme.ts 增加 applyCodeFont(font) 实现。

拓展性分析

新增什么 / 哪里会卡 / 未来怎么走

9.1 新增什么很容易

✅ 新增 capability(强)

注册表新增条目。REST / MCP / agent 三处零改动。
新增成本:1 行 @capability(reg, name, description, ...)。

✅ 新增资源类型(sources 子模块)

services/sources/modules/<type>/ 新建自包含目录(capabilities.py / store.py / worker.py 可选)。
聚合层只多一行 registry.merge(...)。

✅ 新增文档类型(office 子模块)

同 sources 模式。共享 DocumentStore + 独立 kind。

✅ 新增建图管线(graph)

services/graph/pipelines/<type>/ 新建。既有管线不受影响。

✅ 新增设置项

服务的 settings.py 加一行 SettingDef(...),前端零改动(动态渲染)。

✅ 新增人格

在 agent/personas/ 加新文件定义 Persona(...),__init__.py 注册。

✅ 新增钩子点

在 HOOK_POINTS tuple 加新项。

✅ 新增 subagent 模式

在 Mode Enum + run_mode 策略分发加 case。

✅ 新增能力元数据

@capability 装饰器参数扩展(reversible / scopes / cost)无需框架改动。

维度 现状 卡点 缓释建议
单进程单体形态 四进程 / 两进程 / 单体可切 多进程形态下内存限流 / 审计不一致 引入 Redis 形态存储(单进程不变)
graph 双管线 code / ai 互不 import,同一 store 新管线增加会改 store schema store 用 JSON 字段兜底,允许额外元数据

总结

基于 4 个并行 subagent 的全量证据汇总

✅ 优点(做得好的)

  1. 服务间 / 平台反向 / agent → services.* / 聚合子模块 4 项横向 import 全部为 0
  2. "一份 Action 模型"严格落地 — 抽查 8 个 rest.py / 9 个 mcp_server.py 全部是 wire() 薄壳
  3. 框架层集中强制鉴权/限流/审计,handler 不可跳过
  4. 隐私例外多层防御(framework + service 双重校验,llm.set_api_key / sources.set_github_token)
  5. 密钥零明文痕迹(测试断言 key 不出能力出口)
  6. trace_id 端到端 5 层命名一致(虽然 AGENT_MAIN 有断链,但事件/错误体/上下文/事件流都正确)
  7. 0 个大杂烩文件,文件级脱耦严格执行
  8. 每条 capability 描述直接锚定 architecture.md 章节,代码即文档
  9. 聚合服务壳零业务逻辑,新增子模块 = 新增目录
  10. 46 个测试文件,~200 用例,核心能力 + 错误路径双覆盖
  11. Parity 在核心业务层(设置/笔记/图谱/资源/LLM)扎实,所有 capability 都过同一注册表
  12. secret 边界双层强制(平台层 SettingsStore + 服务层 _actor),不靠提示词约束
  13. subagent 工具面真裁剪(Toolbelt.trimmed 真的从工具字典里删)
  14. actor 不可变性广覆盖(frozen=True 跨包),提权阻断机制到位
  15. 事件流驱动 UI 刷新(note.*/task.*/settings.changed/graph.engine.fallback 全部正确发布订阅)

❌ 缺点(必须修的)

  1. Parity 在 chrome 体验层 12 项失败(用户能 / agent 不能):关闭 AskUser、清空草稿、急停、collapse、FloatingChat、Electron...

  3. SECRET_KEY 无长度校验,空串能开仓
  4. AGENT_MAIN 不传 trace_id,跨服务审计/调试断链
  5. 无 kill switch / 急停,长任务无安全阀
  6. apps/desktop/ 目录完全空白,Electron 端 Parity 无法验证
  7. AppPolicy.allowed UI 入口缺失,用户只能到 subagent 工具面级
  8. applyCodeFont 未实现(隐藏 bug)
  9. deploy/backend.py 跨服务 import 8 服务,§3.3 与 §13.1 规则冲突
  10. graph/engines/python/engine.py 725 行 + 品牌名硬违规
  11. sources 缺 mcp_server.py,agent MCP 消费能力缺失
  12. compressor.py 第二刀可能死循环(极端 context 溢出)
  13. code_exec.run_* 未标 long_running=True,框架不校验
  14. runtime/recovery.py 死代码(with_retry / CircuitBreaker 无调用方)
  15. hooks/triggers.py fire 未消费 pre_tool 返回值(空转)
  16. master/proactive.py 硬编码中文 + emoji(违反全局规则)

  18. HealthMonitor 与 HealthProbe 并存(语义重叠)
  19. 跨进程 restrict 强制未测(提权阻断机制存在但无跨进程测试)
  20. RuntimeEvent 与 DomainEvent 命名风格分裂(小写点分 vs PascalCase)

③ 4 个接缝 / 2 个真正瓶颈

独立开发的"必须约定"

3.1 4 个"接缝"(团队约定即解决)

接缝 当前约定 独立开发时的风险 缓释
① capability 注册表冲突 name 强校验 ^[a-z][a-z0-9_]*$;Registry.register 冲突抛 CONFLICT 两个开发者定义同名 capability 合并时冲突 约定 namespace 前缀(如 notes__*、graph__*);CI 检查重复
② 事件类型词汇表 DomainEvent 11 字符串 + RuntimeEvent 11 字符串 新事件类型字符串拼写不一致 所有事件类型经 platform_contracts;测试覆盖 to_dict/from_dict
③ 设置项 schema SettingDef key 强校验 ^[a-z][a-z0-9_]*(\.[a-z0-9_]+)+$ 新 key 命名不一致(如 notes.Sort vs notes.sort.default) 沿用 <service>.<config> 二级格式;docstring 必填
④ 前端类型契约 由 platform/contracts 推导 TS 类型 前端 store 类型与后端 capability 返回不一致 前端所有类型从 callCapability<T>() 推断;后端改字段必须同步通知前端

3.2 2 个真正瓶颈(需要先解决)

🔴 瓶颈 #1 · deploy/backend.py 跨服务 import

deploy/backend.py:55-62 在 build() 函数体内一次性 import 8 个服务的 wire_xxx。 这意味着"独立开发"必须从 deploy/ 入手——任何 1 个服务未实现,deploy.backend 都不能跑。 绕开方案:开发时 python -m services.<domain> 直接跑单个服务;CI 用 deploy/ 跑集成,但不强求每个 PR 都过集成。

🟡 瓶颈 #2 · CSS 锁定(唯一前置条件)

前端 9 page 已具备完整业务逻辑,store/provider/hooks 全部就位; 但视觉风格尚未定。在样设未确定前,独立开发会遇到: page 内部用临时类名(如 chat-page、note-list__item),后期样设落地要全部改写类名; 组件布局假设了"两栏/三栏"等模式,样设改变可能涉及组件树重构。

这就是为什么"样设先行"是必要的: 把视觉风格 + 设计 token + 布局规则先固化到 styles/ 与 shell/,page 只需要套用现成的 token 与布局组件即可。 没有样设先行的"独立开发"会出现两种糟糕情况: ① 9 个 page 各自实现一套样式,后期整合时大量冲突;② 9 个 page 都按样设负责人的风格改,负责人失去话语权。

④ 能否先完成样设迁移?

结论:能,而且是最优路径(也是唯一推荐路径)

用户的方案"先完成前端整体样设的迁移,然后分模块独立完成每个模块的前后端"—— 这恰好是 Voyager 架构已经为这种工作流准备好的最优路径。 bridge 边界、page 五件套、shell 容器、styles 3 文件 78 KB 都已经"在合适的位置等样设"。

✅ 一句话结论: 样设先行是最优路径,不是可选项。Voyager 前端的 78 KB 现有 styles + 50 KB shell/widgets 已建立"待填充"的容器, 只要把 RepoPilot 旧前端的"视觉风格"提取为 design tokens 并落进 styles/design-system.css, 9 个 page 几乎可以无修改套用;再分模块并行完成业务即可。

4.1 样设迁移的"接缝"已经存在

① styles/design-system.css 已 44 KB

已有完整的设计系统主样式,包含色板、字体、间距、圆角、阴影、动效等基础 token。样设迁移的主要工作是扩展与替换这部分,不是从零写。

② styles/shell.css 已 30 KB

壳布局(导航栏、侧边栏、顶栏、内容区、悬浮窗)已建立完整样式,样设只影响"美学表达"不影响"骨架结构"。

③ shell/AppShell.tsx + shell/ServiceBadge.tsx + shell/Degraded.tsx + shell/useTheme.ts

壳层 React 组件已具备,样设只影响 className 与 CSS 变量值。结构稳定,主题切换(useTheme)已实现 settings.changed 事件热切换。

④ widgets/ 已有 FloatingChat + PageProbe + 3 个 chat 共享组件

共享组件已建立,样设不影响其 props 形态。

⑤ main.tsx 入口极简(22 行)

仅 useTheme 钩子 + 3 个 styles 引入;改样设不影响 main.tsx 业务逻辑。

⑥ App.tsx 路由表极简(35 行)

每个 page 一行 import + 一行 route;不改样设不影响路由。

4.2 样设迁移的边界

层级 是否在样设迁移范围 理由

⑨ 总结

两个问题的最终答案 + 落地路径

✅ 问题 1:能否每个模块独立开发?

能,且已为这种工作流做好完整准备。

  • 横向 import 矩阵 4 项全 0(语言层强制)
  • 每个 services/* 有完整七件套,可独立启动
  • 每个聚合子模块自包含
  • 每个前端 page 五件套,App.tsx 1 行/page
  • bridge 边界隔离 9 个 page 互不依赖
  • platform 7 包依赖方向严格向下

7 大类 40+ 独立开发单元,5-7 人峰值并行。

✅ 问题 2:能否样设先行 + 分模块?

能,而且是最优路径。

  • 78 KB 现有 styles + 50 KB shell/widgets 是"待填充容器"
  • 样设与业务几乎完全解耦(bridge、store、provider 不变)
  • 样设先行能避免 9 个 page 各自实现样式
  • 样设 1 人 · 3-5 天即可完成 token + 通用组件

5 阶段路径 · 6-8 周 · 5-7 人峰值并行。

9.2 关于"每个模块独立开发"的可证伪承诺

如果担心"理论能独立,实际有依赖",可用以下 3 个最小验证 立刻检验:

  1. 克隆到新环境,只装 platform/* 7 个 uv workspace + services/notes,运行 python -m services.notes;若 30 秒内启动,说明 notes 真的独立。
  2. 克隆到新环境,只装 platform/* 7 个 + 装 apps/web,npm run build;若 30 秒内构建,说明前端不依赖任何具体 service。
  3. 删除 apps/web/src/pages/notes 整个目录,npm run build;若其他 page 仍能构建,说明 page 完全独立。

三个验证都能通过,独立开发承诺就是工程事实,不是纸面承诺。

📌 最终结论: Voyager 的架构设计已经为"分模块独立开发 + 样设先行"做好了全部准备。 横向 import 矩阵 0、bridge 边界隔离、page 五件套、聚合服务壳零逻辑、platform 依赖方向严格向下——这些不是"努力维持的纪律",是语言层阻断(空 __init__.py + 唯一包名 + capability 框架)。 样设先行 + 业务分模块并行是推荐路径,不是可选项; 没有样设先行的"独立开发"会出现 9 套重复样式冲突、负责人失语、后期重构成本激增。 5 阶段 6-8 周路径,峰值 5-7 人并行,立即可启动。
